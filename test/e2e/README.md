# End to end: `canal` mode against the real portal

`canal-e2e.mjs` tests the `canal` mode deliverable (K1 exit criterion) against the portal's development stack (`../data-exchange`):

1. `elena.admin` registers a node and receives the token.
2. The node starts with the `den-node:<v>-canal` image (`compose.yaml`). It runs without capabilities, with a read-only file system, without root and without published ports.
3. The node enrolls, brings up the tunnel with the real hub, sends heartbeats and goes `online`.
4. The node serves the portal's test provider (`mock-salud`) as if it were the entity's own API (`config/node.yaml`).
5. A version with `upstream: node` is published and passes review.
6. A consumer subscribes and calls through the gateway.
7. The node's log is checked: the gateway appears by its name, the path appears as a template, and the document number does not appear.
8. `status` and `doctor` are run inside the container.

```
# in ../data-exchange: pnpm infra:up and the API (pnpm dev)
make e2e
```

At run time, the script writes the token to `.run/` and copies the portal's OpenAPI into `config/`. Both are in `.gitignore`.

Each run leaves in the portal a node `prueba-kit-canal-*`, an API "Afiliación por el canal (prueba del kit …)", an application and a subscription, all with synthetic data. The test is left as it finished, with the node `online`. With `DEN_E2E_CLEANUP=1`, it revokes the subscription, decommissions the node and removes the local containers.

## Against the deployed portal (VPS)

With `DEN_E2E_TARGET=vps`, the node runs on this machine, as it would at an entity. It goes out over the internet to the public portal, gateway and hub (`compose.vps.yaml`, `config-vps/node.yaml`), and the entity's own API is the test provider, running next to it.

Variables, taken from the deployment's `.env`:
- `DEN_API_URL`, `KEYCLOAK_URL` (`…/auth`), `DEN_GATEWAY_PUBLIC_URL`, `DEN_GATEWAY_HTTP_URL` (`…/gw`) and `DEN_WEB_URL`;
- the secrets `DEN_PORTAL_WEB_CLIENT_SECRET`, `DEN_DEMO_USER_PASSWORD` and `DEN_DEMO_TOTP_SECRET`.

The secrets are not stored in the repository.

## Clean installation with the installer

With `DEN_E2E_NODE=installer`, the node is installed with `install.sh` from the bundle (`make bundle`), on a test server (`test/install/ubuntu.sh`):
- **`DEN_TEST_DOCKER=preinstalled`** (default): an Ubuntu 24.04 with Docker already installed.
- **`DEN_TEST_DOCKER=install`:** an Ubuntu 24.04 with systemd as PID 1 and **no Docker**. The installer installs Docker Engine from `download.docker.com`.

The test goes through:
1. a wrong token and then the right one;
2. reinstallation;
3. `service` and `service remove`;
4. `update` to a version that does not exist;
5. losing the state and `restore`;
6. the mode change;
7. publication and consumption through the gateway.


## Instant API (`completo` mode)

With `DEN_E2E_SERVICE=instant` (together with `DEN_E2E_NODE=installer`), the test closes K3:
1. Installs the node in `completo` mode on a clean test server (`DEN_TEST_SERVER`, by default `den-install-test`).
2. Brings up the entity's database on that server: PostgreSQL with the synthetic data from `test/engines/postgres`, on the node's network, and a `den_reader` user that can only read the views.
3. Runs `install.sh service` of type `instant` on `salud.v_afiliados`, with key `numero_documento` and data subject `CC`.
4. Publishes in the portal the OpenAPI generated by the installer and waits for the heartbeat to carry its hash.
5. Checks that the consumer receives the view's row through the gateway, and that the node's log has the template `/salud/afiliados/{numero_documento}` and not the document number.
6. Runs `status` and `doctor`. `doctor` checks the connection, the catalog, that the user cannot write, and the read-only transaction.

```
DEN_E2E_TARGET=vps DEN_E2E_NODE=installer DEN_E2E_SERVICE=instant DEN_TEST_SERVER=den-install-instant node test/e2e/canal-e2e.mjs
```

With a different `DEN_TEST_SERVER`, the server from a previous run is left as it was.
