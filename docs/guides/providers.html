What a provider entity designates, provides and does to publish its data

The central platform (portal and gateway) is run by the national operator. The only thing the provider installs is the node, inside its own network. What a consumer entity does is covered in the portal's entities guide.

Before the day

1What being a provider means

It publishes an APIOver its data. Its data steward decides who gets access, for what purpose, to which operations and for how long.
It knows who is queryingOn every call, the gateway tells it the entity, the application, the authorization and the purpose.
The data staysIt is never copied to the platform: each query reaches the entity, and the response passes through the gateway without being stored.
Accountable to citizensCitizens can see which entity queried their data and why.

2People the entity must designate

entity_admin
Head of IT or of the data office

Requests the entity's registration, invites its people, assigns roles and registers the node.

data_steward2nd factor required
Data steward (formal designation)

Approves, rejects, suspends and revokes access to the entity's APIs.

api_publisher
Technical lead

Registers the APIs and submits them for review.

Infrastructureno portal account
Server and network administrator

Installs and operates the node.

  • Everyone with an account needs their own institutional email address: the account is verified by email, and invitations are sent to that address.
  • The second factor is set up with an authenticator app (FreeOTP, Aegis, Google Authenticator or any other TOTP app) on the person's phone.
  • Document: the formal act designating the data steward and the technical lead, as a PDF. It is attached to the registration request.
  • If the entity will also consume, it additionally needs an app_developer (portal's entities guide).

3How the service connects: the node

Every provider entity connects through the node: a small service installed inside the entity's network that opens the tunnel outward. The entity opens no inbound ports.

Outbound, not inboundThe node opens the encrypted tunnel (WireGuard) to the network's hub. No inbound ports.
Serves only the gatewayIt accepts only the gateway certificate issued for the entity. Any other client is rejected.
The credential stays insideIf the internal API requires a credential, the node adds it. It never leaves the entity.
Stores no contentIts logs hold only metadata: which operation, when, with what result.
Renews itselfIts certificate is renewed before it expires, and the portal sees whether it is online.

canal mode

available

The entity already has a REST API, its own or built with any tool.

  • The node provides the secure channel and hands each query to the API, at its internal URL.
  • Image without database drivers. The mode can be changed later without losing the node's identity.
  • The entity is accountable for its API and for its OpenAPI contract.
Available

completo mode

instant APIs

The entity has no API, or has both.

  • The node answers by-key queries over the views the entity chooses, with a read-only user: SQL Server, PostgreSQL, MySQL or Oracle.
  • It generates the API and its OpenAPI. The entity decides which columns go out by creating the view.
  • It also serves the entity's own APIs.
Available

Other connections

without a node
  • X-Road: if the entity already publishes on X-Road, the gateway reaches it through the operator's Security Server.
  • Directly exposed API: an exception agreed with the operator. It requires HTTPS with a public certificate, inbound traffic from the gateway's IP and, preferably, mTLS with CN=den-gateway.<slug>.

4What the entity must provide

Server for the node

SystemUbuntuServer 22.04 or 24.04 LTS, amd64 or arm64, dedicated to the node. With only Windows Server, a VM running Ubuntu
Size1 · 1 · 5vCPU, GB of RAM and GB of disk
DockerEngineIf it is missing, the installer installs it from download.docker.com. The snap version does not work
Access and timesudo · NTPWith a skewed clock, certificates fail

The server must reach the entity's internal API (canal mode) or its database (completo mode).

Network: outbound only

51820/udpTo the network's hubThe tunnel. Essential; it does not go through an HTTP proxy.
443/tcpTo the portal and the gatewayEnrollment, heartbeat and renewal. It can go through the corporate proxy, if the proxy accepts CONNECT without a username or password.
internalTo the entity's APIWhat the node publishes with an own API, inside the entity's network.
1433 · 5432 · 3306 · 1521To the databaseThe instant APIs: SQL Server, PostgreSQL, MySQL or Oracle, or whatever port the entity uses.

No inbound port is opened. The operator provides the names of the portal and the gateway.

The service being published

WhatDetail
OpenAPI 3 contractThe portal checks it when the version is registered: an operationId on every operation, with no duplicates; at least one success response; only local $ref; in APIs with personal or sensitive data, each operation declares its data subject (x-den-data-subject) or none.
IdentifiersNever in the query string. Document numbers go in the path (/personas/{documento}) or in the body of a POST, not in ?documento=….
Own APIThe API's internal URL and, if it requires one, its credential: a header, a username and password, or a client certificate.
Instant APIOne view per query, with only the columns that will be shared, and a read-only user with SELECT on those views and nothing else. The node generates the OpenAPI. The commands for each engine are in docs/INSTANT-APIS.md.
A sandbox is advisable

The same service with synthetic data, published through the same node as one more service. The portal uses it to test the contract when the API is submitted for review, and consumers integrate without touching real data.

During the day

6Check the network from the node server

The operator hands out the platform's two names, the portal's and the gateway's, the node bundle with its SHA-256 checksum, and the entity-check.sh script, which only needs bash, curl and openssl.

chmod +x entity-check.sh
./entity-check.sh check <portal> <gateway>

It checks DNS, outbound HTTPS to the portal and the gateway, and that the gateway's certificate verifies against the network's root.

The tunnel cannot be tested yet

The script does not test UDP 51820 without a node. The node itself checks it after it is installed, with sudo /opt/den-node/install.sh doctor.

7Registering the entity and its people

  1. The future entity_admin goes to https://<portal>, creates an account and confirms the email address.
  2. They request the entity's registration: details, designated people and the designation document. The operator reviews and approves it. If the entity has already been onboarded by a formal act, the operator registers it directly.
  3. The entity_admin invites each person by email and assigns them roles. Each invitee creates an account with that same email address and accepts the invitation.
  4. The data_steward sets up their second factor the first time the portal asks for it.

8Install the node

  1. The entity_admin goes to My entity → Kit nodes, registers the node and copies the enrollment token. It is shown only once, works for a single node and expires in 72 hours. They pass it to the infrastructure team through a secure channel.
  2. The infrastructure team verifies the bundle against the checksum published by the operator and installs it. The installer asks for the mode (canal or completo), the proxy, the portal URL and the token. 
    sha256sum den-node-kit-<version>.tar.gz
tar -xzf den-node-kit-<version>.tar.gz
cd den-node-kit-<version>
sudo ./install.sh
  3. Add the service, and its sandbox if there is one. With an own API (proxy) it asks for the name, the path on the node (for example /certificados), the internal URL, the credential and the OpenAPI. With an instant API (instant) it asks for the database connection with the read-only user, shows the views it can read, asks for the view and the key column, and generates the OpenAPI in /opt/den-node/config/services/<name>.openapi.json. 
    sudo /opt/den-node/install.sh service
  4. In the portal, the node shows as Online.
Node installation guide

The details of each question, the corporate proxy, backup, updates and common problems are in docs/INSTALL.md, which also ships inside the bundle. Preparing the database, the service file, the types and the responses of the instant APIs are in docs/INSTANT-APIS.md.

9Publish an API

draft→ in review→ approved by the operator→ approved by the regulator · if sensitive→ published
  1. The api_publisher creates the API and its version: uploads the service's OpenAPI (the same one given to the node for an own API, or the one the node generated for an instant API); under Where does the service live? chooses Node of the instant-APIs kit (canal mode uses the same option), the node and the Service path on the node; under Test service (sandbox), the same node and the sandbox path; fills in the classification (public, internal, personal or sensitive), the exposed data, the legal basis and the permitted purposes.
  2. Submits it for review. The portal tests connectivity through the gateway and the node, and the contract against the sandbox. If anything fails, the publisher fixes the service and clicks Run validations again.
  3. The operator reviews and approves; if the API is sensitive, the regulator does too. The API is published and its route exists on the gateway within seconds, closed until there is approved access.
  4. The data_steward receives the consumers' access requests and decides each one: purpose, operations and validity period.
  5. The printable sheet (Catalogue → the API → Service sheet) serves for the records.
Does it fail with 502 right after the node is installed?

The network takes a few seconds to learn about a new node. Wait a minute and click Run validations again.

10What the service receives on each query

The gateway sets these headers and removes any the consumer tries to send. The node passes them unchanged to the entity's API. The consumer's credential (Authorization) never reaches the API: it stays at the gateway.

HeaderContent
X-DEN-Consumer-Entity
X-DEN-Consumer-App		Consumer entity and application
X-DEN-SubscriptionThe authorization under which the query was made
X-DEN-PurposeDeclared purpose
X-DEN-OperationContract operation (operationId)
X-DEN-End-User-HashHash of the official making the query, if the API requires it
X-DEN-Subject-RefPseudonym of the data subject, if the operation declares one
X-Request-IdCorrelation identifier, the same as in the network's log

Later on, the gateway will sign each call in an X-DEN-Assertion header, so the entity can prove who queried it and verify that the query comes from the gateway.

11Recommendations for the entity's service

The network cannot verify what happens inside the entity. These practices are recommendations, and the node's completo mode meets them by design.

MinimizationReturn only the fields that the service sheet declares.
No content in the logsNo request or response bodies. Paths and query strings masked: they can contain identification numbers.
Read-onlyThe API reads the data with a read-only user.
Only through the nodeThe API is not exposed outside the internal network: the node is its only door to the network.
Keep traceabilityLogging X-Request-Id, X-DEN-Consumer-Entity and X-DEN-Purpose with each query lets you answer an audit.

12The entity's commitments

Decide on accessThe data_steward approves only legitimate purposes with a legal basis, and revokes access when it is no longer appropriate.
Node onlineWith no signals for 5 minutes, the portal marks it Offline and alerts the administrators. If the portal requires a minimum kit version, update.
Node backed upThe backup contains the node's keys: copy it off the server and keep it as a secret.
Announce changesAn incompatible change in a published API requires a new major version. The previous one is deprecated with a retirement date.

13Operating the node

sudo /opt/den-node/install.sh statusStatus: portal, tunnel, certificate, health of each service and warnings.
sudo /opt/den-node/install.sh doctorChecks the configuration, secrets, DNS, portal, clock, internal APIs and tunnel.
sudo /opt/den-node/install.sh logsThe node's latest logs (metadata only). With -f it follows them live.
sudo /opt/den-node/install.sh backupBackup in /opt/den-node/backups/, with the node's keys.

To report a problem to the operator, attach the output of status and doctor: it contains no secrets and no personal data.
