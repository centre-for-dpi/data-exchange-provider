Antes de crear el servicio

1Qué publica el nodo

El nodo lee una vista (o una tabla) de la base de la entidad y la publica como una consulta por clave: GET {ruta del servicio}/{recurso}/{clave}.

GET /afiliacion/afiliados/1000000001→ el nodo valida la clave→ SELECT … WHERE numero_documento = ? · solo lectura→ vista salud.v_afiliados→ JSON con las columnas declaradas 
GET /afiliacion/afiliados/1000000001
→ 200 {"numero_documento": "1000000001", "eps": "EPS01", "regimen": "contributivo", ...}

A través del gateway, el consumidor llama a /<entidad>/<api>/v1/afiliados/1000000001. La ruta exacta está en la ficha de la API en el portal.

Cuatro motoresSQL Server, PostgreSQL, MySQL y Oracle. No hace falta instalar ningún cliente en el servidor: los drivers van dentro del nodo. Probados: Oracle 11g, 21c y 23ai; SQL Server 2019; PostgreSQL 17; MySQL 8.4.
Un servicio, una conexiónCada servicio se conecta a una base y tiene uno o varios recursos. Cada recurso es una vista y una clave.
OpenAPI generadoEl nodo genera el contrato que se sube al portal, y ya cumple las reglas de la red.
Solo por claveNo hay listados, filtros, búsquedas ni escrituras.

2Preparar la base de datos (DBA)

La vista

La vista es el contrato

Lo que no está en la vista no sale. Incluye solo las columnas que se van a compartir, con la minimización que declara la ficha del servicio.

  • Nombres simples: letras, números y _, empezando por una letra o _ (numero_documento, no "Número documento"). Una columna con otro nombre se renombra en la vista con AS.
  • La columna clave debe ser de texto, entero, numérico sin decimales, UUID o fecha. Si es de texto, conviene que solo use letras, números y guiones (sección 6).
  • Clave única, salvo que el recurso se declare con varias filas por clave (por ejemplo, un hogar con varias personas).
  • Un índice sobre la columna clave en la tabla de origen: cada consulta es un WHERE clave = ?.

El usuario de solo lectura

Un usuario propio para el nodo, con SELECT sobre las vistas que se exponen y nada más. Sin roles amplios como db_datareader y sin permisos sobre las tablas de origen: la vista ya se lee con los permisos de su dueño.

PostgreSQL

CREATE ROLE rid_reader LOGIN PASSWORD '<contraseña>';
GRANT CONNECT ON DATABASE entidad TO rid_reader;
GRANT USAGE ON SCHEMA salud TO rid_reader;
GRANT SELECT ON salud.v_afiliados TO rid_reader;

SQL Server

CREATE LOGIN rid_reader WITH PASSWORD = '<contraseña>';
USE entidad;
CREATE USER rid_reader FOR LOGIN rid_reader;
GRANT SELECT ON salud.v_afiliados TO rid_reader;

MySQL

el "esquema" es la base de datos
CREATE USER 'rid_reader'@'<IP del nodo>' IDENTIFIED BY '<contraseña>';
GRANT SELECT ON salud.v_afiliados TO 'rid_reader'@'<IP del nodo>';

Oracle

en la PDB; la "base" es el servicio (p. ej. ORCLPDB1)
CREATE USER rid_reader IDENTIFIED BY "<contraseña>";
GRANT CREATE SESSION TO rid_reader;
GRANT SELECT ON salud.v_afiliados TO rid_reader;
  • La contraseña no se escribe en ningún archivo de configuración: el instalador la pide sin mostrarla y la guarda en /opt/rid-node/secrets/<servicio>_db_password.
  • doctor comprueba que el usuario no pueda escribir en las vistas que se exponen. Si puede, lo marca con ✘.

3Modo del nodo

Las APIs instantáneas necesitan el nodo en modo completo. Si se instaló en modo canal, se cambia sin perder la identidad ni los servicios:

sudo /opt/rid-node/install.sh modo completoCambia a la imagen con las APIs instantáneas y los drivers.
sudo /opt/rid-node/install.sh servicioTipo instant: muestra las vistas que el usuario puede leer, crea el recurso y genera el OpenAPI en /opt/rid-node/config/services/<servicio>.openapi.json.
Configuración

4El archivo del servicio

Cada servicio vive en /opt/rid-node/config/services/<servicio>.yaml. El instalador lo escribe; se puede editar después (sección 8).

name: afiliacion                       # nombre del servicio: minúsculas, números y guiones
path: /afiliacion                      # "Ruta del servicio en el nodo" en el portal
type: instant
title: Afiliación en salud             # opcional: título del OpenAPI (por defecto, el nombre)
description: Consulta de afiliación    # opcional
version: 1.0.0                         # opcional: versión del OpenAPI (por defecto 1.0.0)
database:
  engine: postgres                     # sqlserver | postgres | mysql | oracle
  host: bd.interna.entidad
  port: 5432
  name: entidad                        # la base; en Oracle, el nombre del servicio
  user: rid_reader
  passwordFile: /run/secrets/afiliacion_db_password
  tls: require                         # disable | require | verify
  # caFile: /run/secrets/afiliacion_db_ca.pem   # solo con verify (no en Oracle)
  maxConnections: 4                    # conexiones simultáneas a la base (por defecto 4)
  queryTimeout: 5s                     # tiempo máximo por consulta (por defecto 5 s)
resources:
  - name: afiliados                    # en la URL: /afiliacion/afiliados/{clave}
    entity: Afiliado                   # nombre en el OpenAPI (esquema y operationId getAfiliado)
    source: salud.v_afiliados          # esquema.vista
    description: Afiliado por documento   # opcional
    key:
      column: numero_documento         # la columna que se busca con la clave
      # pattern: '[0-9]{6,12}'         # opcional: formato propio de la clave
    dataSubject: { documentType: CC }  # si la clave identifica a una persona
    many: false                        # true: la clave trae una lista
    # maxRows: 100                     # con many: máximo de filas (por defecto 100, hasta 1000)
    columns:
      - { name: tipo_documento }
      - { name: numero_documento }
      - { name: eps }
      - { name: activo, as: boolean }  # as cambia cómo se publica la columna (sección 5)
Campo del recursoQué es
nameEl nombre del recurso en la URL. Minúsculas, números y guiones, máximo 80
entityEl nombre en el OpenAPI. Empieza por mayúscula, solo letras y números, único en el servicio (Problem está reservado)
sourceLa vista o tabla, como esquema.objeto. Las mayúsculas no importan
key.columnLa columna clave. Debe estar en la vista
columnsLas columnas que se publican. Una columna que no está aquí no sale, aunque esté en la vista
dataSubject datos personalesDeclara que la clave identifica a una persona y con qué tipo de documento. El portal lo exige en APIs personales o sensibles. Sin él, el OpenAPI declara que el recurso no tiene titular
many opcionaltrue si una clave trae varias filas. La respuesta es una lista
Todo o nada

El archivo se valida completo antes de aplicarlo. Si algo no coincide con la base (una vista que no existe, una columna mal escrita, un as que no se puede aplicar), el nodo no sirve ningún recurso del servicio, y validate y doctor dicen por qué.

6La clave

La clave llega en la URL y se valida antes de consultar la base. Un formato inválido da 400 sin tocar la base.

Tipo de la columna claveFormato que acepta por defecto
TextoLetras, números y guiones, hasta el largo de la columna. Sin espacios, comillas ni separadores
Entero o númeroHasta 38 dígitos. Una clave que no cabe en la columna da 404 sin consultar la base
UUIDxxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
FechaAAAA-MM-DD

Si las claves de la entidad tienen otro formato (por ejemplo, con puntos o letras al final), se declara key.pattern con una expresión regular. El nodo la ajusta a la clave completa. Ninguna clave puede pasar de 256 bytes.

7Cómo responde la API

RespuestaCuándo
200 objetoLa clave existe (recurso sin many)
200 listaLa clave existe (recurso con many). La lista sale ordenada por sus columnas, siempre en el mismo orden
404 not_foundLa clave no existe, o el recurso no existe
400 invalid_keyLa clave no tiene el formato del recurso
400 query_not_allowedLa URL trae parámetros (?...). Las claves van siempre en la ruta
405 method_not_allowedUn método distinto de GET
500 non_unique_keyUna clave declarada única trajo dos filas. Revisa la vista, o declara many: true
500 too_many_rowsUna lista pasó de maxRows. Nunca se corta en silencio
500 response_too_largeLa respuesta pasó de 8 MiB
500 unrepresentable_valueUn valor de la base no cabe en el tipo que declara el OpenAPI (por ejemplo NaN, Infinity o una fecha 0000-00-00). El log dice qué columna, nunca el valor. Corrígelo en la vista, por ejemplo con NULLIF
503 service_unavailableLa base no responde, o el archivo del servicio no coincide con la base (una columna cambió, o el usuario no tiene SELECT sobre la vista)
  • Los errores van en application/problem+json, con un título en español y un code estable.
  • GET {ruta del servicio}/ responde {"status":"ok"}, o 503 si la base no responde: es lo que usa el portal para saber si el servicio está sano.
  • Si la base se cae, el servicio contesta 503 y el portal lo ve con problemas. Cuando la base vuelve, el servicio se recupera solo, sin reiniciar el nodo.
Operación

8Cambiar un servicio

Los comandos del nodo se ejecutan dentro del contenedor, desde /opt/rid-node. Dentro del contenedor, la configuración está en /etc/rid-node/services/.

cd /opt/rid-node
sudo docker compose exec rid-node /rid-node <comando>
ComandoPara qué
catalog --service-file /etc/rid-node/services/<servicio>.yamlLas vistas y tablas que el usuario puede leer, con sus columnas y si se pueden publicar
scaffold --print --service-file ... --source esquema.vista --key columna [--resource nombre] [--entity Nombre] [--subject CC] [--many]Imprime el archivo del servicio con un recurso nuevo, que trae todas las columnas que se pueden publicar
validateValida todos los servicios contra sus bases
openapi <servicio>Imprime el OpenAPI que se sube al portal

Quitar o ajustar columnas

Edita config/services/<servicio>.yaml: quita la columna de columns, o agrégale as.

Agregar un recurso a un servicio existente

Otra vista sobre la misma base:

sudo /opt/rid-node/install.sh servicio recurso afiliacion

Muestra las vistas que el usuario puede leer, pide la vista y su clave, agrega el recurso, valida, regenera el OpenAPI y reinicia el nodo. Si algo falla, deja el servicio como estaba. El OpenAPI cambia, así que hay que publicar una versión nueva en el portal.

Después de cualquier cambio

  1. Valida, regenera el OpenAPI y reinicia: 
    cd /opt/rid-node
sudo docker compose exec rid-node /rid-node validate
sudo docker compose exec rid-node /rid-node openapi afiliacion | sudo tee config/services/afiliacion.openapi.json >/dev/null
sudo docker compose restart rid-node
  2. Si el OpenAPI cambió, publica una versión nueva en el portal. El nodo envía la huella del OpenAPI que sirve en cada heartbeat, para que el portal sepa qué contrato está detrás. Un cambio incompatible (quitar una columna, cambiar su tipo, cambiar la clave) exige una versión mayor nueva.
Si cambia la vista en la base

El servicio sigue sirviendo las columnas declaradas. Una columna nueva en la vista no se publica hasta que se agrega a columns. Si se quita de la vista una columna declarada, el servicio deja de servir y doctor dice cuál falta.

9Seguridad y privacidad

Solo lectura en tres capasEl usuario de la base, que doctor verifica; una transacción de solo lectura en cada consulta (PostgreSQL, MySQL y Oracle; SQL Server no la tiene); y un SELECT generado por el nodo con la clave como único parámetro. Los nombres de vistas y columnas salen del catálogo, nunca de la petición.
Sin contenido en los logsEl recurso, la plantilla de la ruta y el resultado; nunca la clave ni los valores. Los errores de la base se registran por clase, no con el mensaje del driver.
Los datos no se copianCada consulta se responde en el momento desde la base de la entidad, y el nodo no guarda nada.
La base se protegeEl nodo limita las conexiones (maxConnections), el tiempo por consulta (queryTimeout) y las peticiones simultáneas.

11Límites de esta versión

  • Solo GET por clave. No hay listados, filtros ni búsquedas por cuerpo (POST).
  • Un recurso nuevo en un servicio existente se agrega editando el archivo (sección 8): el instalador solo crea servicios nuevos.
  • Oracle se probó con la versión 23ai. Con versiones más antiguas, se prueba con cada entidad.
  • En PostgreSQL, las columnas timestamp with time zone salen en UTC.
