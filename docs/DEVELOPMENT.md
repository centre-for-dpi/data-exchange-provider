# Kit development

> Versión en español: [docs/es/DEVELOPMENT.md](es/DEVELOPMENT.md)

## Requirements

- Go 1.27.
- Docker Engine for the images and the end-to-end tests.
- `make` on Linux. On Windows, you can run the same `Makefile` commands by hand.
- For the end-to-end test: the portal repository at `../data-exchange`, with its stack up (`pnpm infra:up`) and its API on `:4000`. Node.js is also needed for the script.

## Layout

| Path | Contents |
| :-- | :-- |
| `cmd/den-node/` | CLI: `run`, `status`, `doctor` and `version` |
| `internal/config/` | `node.yaml`, validation and file-based secrets |
| `internal/state/` | Persistent state (atomic writes, 0600) and `status.json` |
| `internal/contract/` | Node contract v1 client, tested against a copy of the portal's OpenAPI (`testdata/`) |
| `internal/tunnel/` | Userspace WireGuard. `tunneltest/` is a hub for tests |
| `internal/server/` | TLS that only admits the gateway, routing by `servicePath` and an access log without content |
| `internal/proxy/` | `proxy` services, to the entity's own API |
| `internal/agent/` | Enrollment, heartbeat, health, renewal, `/config` and state. `fakeportal/` is a portal for tests |
| `internal/testpki/` | In-memory PKI for tests |
| `tools/licensecheck/` | License check of the Go modules (rule 1) |
| `tools/imagearch/` | Checks that the binary in each image of the bundle is for the image's architecture |
| `deploy/` | Dockerfile for both variants |
| `test/e2e/` | End-to-end test against the real portal |
| `spikes/` | Throwaway code from ADR-0001. Not part of the kit |

## Commands

```
make build build-canal     # binaries in bin/
make test                  # tests for both variants (completo and canal)
make check                 # gofmt, vet, go mod verify, tests, licenses, vulnerabilities and canal guard
make image image-canal     # images den-node:<version> and den-node:<version>-canal
make e2e                   # canal image + end to end against the real portal
make test-engines          # instant APIs against real SQL Server, PostgreSQL, MySQL and Oracle
make bundle                # delivery bundle in dist/ (both variants, amd64 and arm64, SBOM and SHA256SUMS);
                           # it stops if an image carries a binary for another architecture
```

### Bundle signature

`make bundle` with `DEN_SIGN_KEY` signs the bundle: `dist/den-node-kit-<version>.tar.gz.sig`. `DEN_SIGN_KEY` is the path to the operator's OpenSSH private key, which never enters the repository. It is signed with `ssh-keygen -Y sign`, in the `den-kit` namespace:

```
ssh-keygen -t ed25519 -C "operador@red" -f ~/.config/den-node/firma   # once, outside the repository
DEN_SIGN_KEY=~/.config/den-node/firma make bundle
echo "operador@red $(cut -d' ' -f1,2 ~/.config/den-node/firma.pub)" > allowed_signers   # published alongside the checksum
```

The images are inside the bundle and covered by `SHA256SUMS`, so signing the bundle also signs the images. Each variant carries its SBOM in CycloneDX format (`sbom-completo.cdx.json` and `sbom-canal.cdx.json`), generated by `tools/licensecheck -cyclonedx`.

### Database engines for instant APIs

`make test-engines` brings up `test/engines/compose.yaml` and runs the integration tests. These are four containers with synthetic data, on `127.0.0.1:55432` (PostgreSQL), `53306` (MySQL), `51433` (SQL Server) and `51521` (Oracle). Then it runs the portal's lint on the OpenAPI generated for each engine. The lint needs the portal repository at `../data-exchange`, with its dependencies installed.

The passwords go in a variables file outside the repository. By default it is `~/.config/den-node/engines.env`, and you can change it with `DEN_IT_ENV`. To create it with random passwords:

```
mkdir -p ~/.config/den-node && umask 077
r() { od -An -N"$1" -tx1 /dev/urandom | tr -d ' \n'; }
printf "DEN_IT_ADMIN_PASSWORD='Den-%s-Aa1'\nDEN_IT_READER_PASSWORD='%s@:/?x'\nDEN_IT_WRITER_PASSWORD='%sWr1'\n" "$(r 8)" "$(r 12)" "$(r 12)" \
  > ~/.config/den-node/engines.env
```

The `den_reader` password contains `@:/?` on purpose, to test that the DSN escapes it. None is longer than 30 characters, the Oracle 11g limit. `make engines-down` removes the containers and their data.

`make test-engines-legacy` runs the same suite against Oracle 11g XE and 21c XE (the compose `legacy` profile), the oldest versions an entity may have.

`make engines-up` first generates a throwaway CA and server certificate in `test/engines/.certs` (`go run ./test/engines/gencerts`, outside git). PostgreSQL starts with TLS using those certificates, to test `tls: verify`. If they are deleted, the engines must be recreated.

The tests cover, on all four engines:
- catalog, lookup by key, lists and difficult types;
- `CHAR` keys, uppercase keys, keys with spaces and `NULL`;
- the database going down and recovering, with a TCP proxy inside the test;
- the read-only transaction and the write check (direct, per column and by role);
- `tls: disable` on SQL Server and `tls: verify` on PostgreSQL.

The engine images (including SQL Server Developer and Oracle Free) are test infrastructure only: they are never bundled in the kit.

### Continuous integration

`.github/workflows/ci.yml` runs on every push to `main` and every pull request:

- **check**: `make check` (gofmt, the `canal` variant without database drivers, `go vet` and the tests in both variants, `go mod verify`, the license policy and govulncheck), plus `go vet` of the integration tests.
- **installer**: `test/install/unit.sh` on Ubuntu 24.04, and both images.
- **engines**: `make test-engines` against the four engines, with passwords generated for that run and the portal's OpenAPI lint (it checks out the portal next to the kit). It runs on `main` and on demand (`workflow_dispatch`), not on pull requests, because of the size of the SQL Server and Oracle images.

The end-to-end test against a deployed portal (`test/e2e`) is not in CI: it needs the deployment and its credentials, and is part of each delivery.

## Variants

- The `canal` variant is built with `-tags canal`. It does not include instant APIs or database drivers.
- `make check-canal-deps` fails if any of them enters its dependency graph.
- The tests run on both variants.

## Contract with the portal

`internal/contract/testdata/node-contract-v1.openapi.json` is a copy of the portal's contract; its README says which commit it comes from. If the portal changes the contract:
1. copy the file again;
2. run `make test`.

The `contract` tests validate the kit's requests and responses against that copy.
